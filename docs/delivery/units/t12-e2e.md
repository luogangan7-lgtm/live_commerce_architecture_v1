## Scenario (one Go test driving admin + storefront + worker processes on one isolated PG)
1. Store created through `create_initial_store` (0065 grants) — merchant logs in (signed MOCK IdP).
2. Merchant creates a product/SKU with stock, a live session, an offer keyword (e.g. A1), opens the claim
   window, binds the session to a Facebook post via the Studio claim-source UI (MOCK binding + route).
3. A **signed** Meta comment webhook "A1+2" for that post hits the real API ingress → consumer → intake →
   claim bundle → private-reply operation planned (MOCK Graph fake records exactly one send; the reply
   text contains the claim link).
4. Buyer opens the claim link in the storefront (locale zh-TW), sees the prefilled cart (qty 2), checks out
   (7-ELEVEN pickup destination), pays with Stripe: MOCK tier via stripetest; SANDBOX tier (card 4242 on
   the real hosted page) when STRIPE_SANDBOX=1 + STRIPE_BROWSER=1.
5. Order CONFIRMED + stock allocated; merchant sees it in orders (C inline UI), marks it shipped (carrier
   seven_eleven_cvs + tracking), buyer sees shipment on the order page.
6. Merchant issues a partial refund; worker completes it (fake or sandbox); merchant sees SUCCEEDED +
   re_ id; buyer sees refunded amount; stock unchanged (§ refund contract).
7. Negative loop checks: a second identical webhook (replay) creates nothing new and sends no second
   private reply; a comment "不要A1" / "A1是不是红色" creates no claim; another tenant cannot read anything.

Evidence: screenshots per step (desktop + mobile for buyer pages), DB fact assertions at each step, log +
storage scans for PII/secrets. Labels: MOCK for Meta and (default) Stripe; SANDBOX variant for Stripe.
test-local mode `--browser-e2e`. Write paths: tests/foundation/browser_e2e_test.go, tests/e2e/**,
scripts/dev/test-local.sh (new mode only). Do not change product code; report product defects with evidence.
